## 1. 基本データタイプ（data_type.html）

### 要求の要約

| 群 | 内容 |
|---|---|
| 整数 | 符号付き `B`(8)・`H`(16)・`W`(32)、符号なし `UB`・`UH`・`UW` |
| 型未定 | `VB`・`VH`・`VW`（8/16/32 ビット）、汎用ポインタ `VP`、関数ポインタ `FP`、`FUNCP`（`W` を返す関数） |
| volatile 版 | `_B` `_H` `_W` `_UB` `_UH` `_UW` `_void`（最適化させない値）。原文の幅コメントに誤りがある |
| 浮動小数点 | `FLOAT`（32）・`DOUBLE`（64） |
| 論理 | `BOOL`（整数）、`Bool`（列挙。False=0、True=1） |
| 識別子・時間 | `ID`・`WID`＝`W`、`MSEC`（ミリ秒）、`STIME`（1985-01-01 00:00:00 GMT からの秒数） |
| 文字 | `TC`＝16 ビット符号なしの TRON 文字コード、`TNULL`＝0（文字列終端） |
| エラー | `ERR`・`WERR`＝`W`、`ErrCode`（32 ビット値または 16 ビットのクラス＋16 ビットの詳細）、`OK`=0 |
| 共通定数 | `CLR`=0x0000、`NOCLR`=0x0008、`DELEXIT`=0x8000 |
| 構造体 | `SIZE`（幅・高さ、各 16 ビット符号付き）、`PNT`（x・y）、`RECT`（4 辺または 2 点の共用体）、`LINK`（`TC` 20 文字の名前＋16 ビットのファイル ID＋16 ビット属性 5 個） |

バイト順・アラインメントは**原文に明記が見当たらない**。`ErrCode` はバイト順ごとに二通りの定義があり、どちらを採るかの説明は読み取れなかった。

### 照合

| 項目 | 既存実装 | 状態 |
|---|---|---|
| 整数型 `B`〜`UW` の幅 | `user/btron/types.mkn` に対応表（`有符八`〜`無符三二`） | 実装済・未検証 |
| `W` の戻り値規約 | 64 ビットレジスタへ符号拡張（`W拡張`）。`W置`・`W読` | 実装済・未検証 |
| `TC`=UH、`TNULL` | 対応表のみ。文字列関数なし | 部分適合 |
| `CLR`/`NOCLR`/`DELEXIT` | `types.mkn` に定数 | 実装済・未検証 |
| `ERR`/`ErrCode` | `user/btron/er.mkn`（`(eclass<<16)|detail`、eclass=-1） | 実装済・未検証（数値は実装依存の選択。OS 編 G0） |
| `SIZE`/`PNT`/`RECT` | `types.mkn` に欄の配置定数（`SIZE_*`/`PNT_*`/`RECT_*`）と `SIZE置`/`PNT置`/`RECT置`、`H置`/`H読`。QEMU 試験 `識試` の 5 項目（H の符号・範囲・隣欄保持、SIZE/PNT/RECT の配置、RECT の共用体）で確認 | 実装済・未検証（欄名は慣用を仮採用、要確認） |
| `LINK` | `get_lnk` が扱う（OS 編 1.6） | 部分適合 |
| `FLOAT`/`DOUBLE` | 言語に浮動小数点なし | 未実装 |
| `Bool`/`BOOL` | `types.mkn` に `False`=0・`True`=1 と正規化の `BOOL化`。試験 `識試` の `Bool=False0True1` | 実装済・未検証 |
| `MSEC`/`STIME`/`VP`/`FP` | 対応表のみ | 部分適合 |

**要確認**: バイト順・構造体のパディング、`ErrCode` の二つの定義の使い分け、`FLOAT`/`DOUBLE` を持つか（持たなければ非適合として理由を記録）、`_B` 等の volatile 版の扱い（機械漢文の `揮發` 読み書きで足りるか）。
**試験**: `識試`（`user/btron_gtid.mkn`）に H・Bool・SIZE・PNT・RECT の 9 項目を追加済み。`ErrCode` の LE 定義（detail が下位 16 ビット、eclass が上位）と全 42 名の eclass=-1・detail 通し番号の 3 項目も追加済み（計 16 項目）。**浮動小数点の方針**: 機械漢文に浮動小数点型が無く、核・互換層とも使わないため、`FLOAT`/`DOUBLE` は**非適合（意図的な未対応）**として記録する。浮動小数点を引数や戻り値に持つ API が現れた段階で、言語側の拡張とあわせて決める。`MSEC`/`STIME` は W（4 B）で、`STIME` の 4 B は `緩時` の `get_tim`/`set_tim` の試験（`時試`）で配置を確認済み。`VP`/`FP` は 64 ビットのポインタとする実装依存の選択（原文は幅を規定せず、機械漢文のポインタに合わせる）。これで §1 の項目は出揃った。
**実装上の注意**: 機械漢文では識別子を `「」` で囲む（ASCII を含む名は必須）。`0 減 1` のような符号付き 64 ビットのリテラル演算は `無符六四` に入らないため、負値は `負値` 術で作る。

## 2. TRON コード（tron_code.html）

### 要求の要約
- 1 バイト文字と 2 バイト文字の混在方式。2 バイトで表せる文字の集合を**文字セット**と呼び、約 45,000 の符号位置を持つ。同一文字の字体差は別の**書体セット**で区別する。
- 日本語は JIS X 0208 を上位集合として含み、符号位置を保つ（JIS X 0208 の 8,836 位置のうち 6,877 が割当済、うち漢字 6,353）。JIS X 0201 の 8 ビット制御集合を流用し、C0/C1 制御域は同規格に従う。全角・半角は別コードでなく**文字幅指定**で表す。
- 制御コード: 無効を表す 00、タブ・改行など書式用。**言語指定コード**は FE 始まりの範囲で 220 種。**TRON 固有のエスケープ**は FF 始まりで、付加情報の印などを導入し、127 種のエスケープ列をサポート。`FF FF` はファイル終端の印。
- 見出し: 2.1 概要（多バイト、文字セット、書体セット）、2.2 既存コードとの関係（JIS X 0201／0208）、2.3 TRON 日本語文字コード（概要・表・説明・その他）。

### 照合

| 項目 | 既存実装 | 状態 |
|---|---|---|
| 文字列の内部表現 | 超漢文は漢字文字列（UTF-8 想定） | 未実装（`TC` との変換層なし） |
| 2 バイト文字・言語指定・エスケープの復号 | なし | 未実装 |
| JIS X 0201/0208 との対応表 | なし | 未実装 |
| `TC` を扱う文字列関数 | なし | 未実装 |

**調査結果（2026-10-29）: 符号表の入手経路は確定**。原文ページ（`tron_code.html`）は `charset=iso-2022-jp` で配信され、取得した本文を `iconv -f ISO-2022-JP -t UTF-8` に通すと**文字化けなしで読める**（WebFetch 経由の要約が化けるのはこの文字コードの誤読が原因）。以前「画像のみ」とした 2.3.2 の符号表は図 2（`gif/ja_code.gif`）で、**符号の構造は 2.3.3 に文章の表として書かれている**。原文のうち、制御コード・ブロック表・言語指定・エスケープは欠落していない。以下は要約（原文は転載しない）。

| 符号領域 | 内容 |
|---|---|
| `0000`〜`0020`、`007F` | 制御コード。第 2 バイトは 1 バイト系・2 バイト系で共通。特別な意味を持つのは `00` 無効（文字列の終端に使う）、`09` タブ、`0A` 改段落、`0B` 改コラム、`0C` 改ページ、`0D` 改行（段落内）、`20` セパレータ |
| 第 1 ブロック（A ゾーン）`2121`〜`7E7E` | 8,836 位置。**JIS X 0208 とコードの位置が完全に同じ**。第 1 バイト `21`〜`27` が非漢字（1〜7 区）、`28`〜`2F` が予約（8〜15 区）、`30`〜`4F` が第 1 水準（16〜47 区）、`50`〜`74` が第 2 水準（48〜84 区）、`75`〜`7E` が予約（85〜94 区）。`2121` は漢字固定ピッチの空白 |
| 第 2 ブロック（B）`8021`〜`FD7E`、第 3 ブロック（C）`2180`〜`7EFD`、第 4 ブロック（D）`8080`〜`FDFD` | 各 11,844／11,844／15,876 位置。B は JIS X 0208 に足りない頻出文字、C・D はさらに低頻度の文字 |
| `FE21`〜`FE7E`、`FE80`〜`FEFE` | 言語指定コード（220 種）。言語・文字属の切替え |
| `FF21`〜`FF7E` | TRON 特殊コード（94 文字）。文章に挿入する |
| `FF80`〜`FFFE` | TRON エスケープ（127 種）。付箋の区切り。TAD の可変長セグメントの先頭（§3） |
| `FFFF` | 数値として -1。EOF |

その他の規定: 日本語はすべて 2 バイトコードで扱い（1 バイトコードは使わない）、全角・半角は文字コードでなく文字指定付箋で表す。空白は 3 種（漢字固定ピッチ `2121`／英字固定ピッチ `00A0`／プロポーショナル `0020`）。NL・HT・空白・NULL 以外の書式制御用コードは使わない。

**残る不足**:
1. 第 2〜4 ブロック（B・C・D）の**文字の割当**は文章にはなく、図 2 の画像か別の資料（TRON コード表）にしかない。A ゾーンは JIS X 0208 そのものなので、**A ゾーンだけなら外部の符号表なしで実装できる**。
2. JIS X 0208 ↔ Unicode の対応表は原文にない。変換表を作るなら出典（Unicode の JIS0208 対応表、または Python/ICU の `euc_jp` 等の既存の表）を決める必要がある。
3. 図 1・図 2 の GIF は未取得（取得は利用者の許可を得てから）。

**実装（第 1 段階、済）**: `user/btron/tcode.mkn` の `TC分類`（16 ビットの TC を 無効／制御／A〜D／言語指定／特殊／ESC／EOF／空白／未定義に分類）と空白 3 種の定数。`識試` に境界値の 8 項目（計 24 項目）。

**実装（第 2 段階、済）**: A ゾーン（JIS X 0208 1983 年版）↔ Unicode の変換。`tools/gen-jis0208.py` が `user/btron/jis0208.mkn`（1 項 4 桁の 16 進で 8,836 項）を生成する。出典は Python の euc_jp コーデック。84 区 5・6 点（1990 年版の追加）を除き、割当は原文の 6,877 字（漢字 6,353）と一致する。`0x2140` は U+FF3C（JIS0208.TXT の U+005C とは違う）。`user/btron/tconv.mkn` の `TC至UC`・`UC至TC`（線形探索）。`識試` に 5 項目（計 29 項目）。B〜D ゾーンの割当は出典が無く未了。

**方針（案、更新）**: (a) 内部は UTF-8 のままとし、境界（TAD・`TC` を取る API）でのみ変換する。(b) 第 1 段階は**構造の復号だけ**: 2 バイトの `TC` 列を分類する関数（制御／A〜D ゾーン／言語指定／特殊／エスケープ／EOF）と、EOF・セパレータ・空白 3 種の定数。適合試験は上の表の境界値で書ける。(c) 第 2 段階で A ゾーンの JIS X 0208 ↔ Unicode 変換表を `tools/` で生成する（出典を決めてから）。(d) B〜D ゾーンは出典が見つかるまで「未対応」と記録する。

## 3. TAD（tad1.html〜tad3.html）

**実装（セグメントの枠、済）**: `user/btron/tad.mkn`。固定長（16 ビットの TC）と可変長セグメント（FF・ID・LEN〈UH〉・偶数長の本体）の読み（`TAD次`）と書き（`TAD可変書`）、ID 定数（`TS_INFO` 0xE0〜`TS_SFUSEN` 0xE9）、ビッグエンディアンの読み書き。予約 ID（0x80〜0x9F）・奇数長・切れた列・容量不足を拒む。`識試` に 4 項目（計 33 項目）。セグメントの中身（文章付箋・図形・管理情報の欄）は未実装。**ラージセグメントの長さ欄は仮**: 原文は図 3 にしかなく、LEN=0xFFFF + UW 4 バイトは TRON の一般的な定義による仮の実装。図の確認が要る。

### 3.1 データ構造の概要（tad1）

- TAD は文章・図形・画像の情報を格納する形式で、**TRON 文字コード列そのもの**（セグメントの一次元の連鎖）。セグメントは**固定長**（制御コード 0x00〜0x20 など広義の文字コード）と**可変長**に分かれる。
- **可変長セグメントは TRON エスケープ**で、先頭バイト **0xFF**、第 2 バイトが**セグメント ID（0x80〜0xFE。0x80〜0x9F は予約）**、続いてデータ本体の**バイト長（偶数になるよう末尾に 0 を詰める）**、データ本体。**65,536 バイト以上**にはラージセグメント（長さ欄の形式が異なる。図のみで形式は未取得）。ID の用途: 文章付箋 0xA0〜0xAF、図形描画 0xB0〜0xBF、そのほか 0xE0〜0xE9。（以前の「ID は 1 バイトが基本」は誤読）
- 複数バイト値は**上位バイトが先**（ビッグエンディアン）と読める。AArch64（リトルエンディアン）との境界で変換が要る。
- 基本型: 符号付き／なし 8・16・32 ビット整数、点、矩形（右・下は含まない半開）、32 ビット色、単位型（正＝cm あたり、負＝inch あたり、0＝未定義）、文字サイズ、拡大率、比。
- 管理情報セグメント: 版番号（BCD）など。主データの前に置く。副 ID・長さ・データの組。
- 入れ子: 下位の要素は上位の属性を継承できる。見え方は表示領域・描画領域で決まる。
- 付加セグメント: 仮身、機能付加、データ付加、設定付加。画像セグメントは色・傾き・拡張・マスクの欄を持つ。
- 見出し: 3.2 TAD（概要、レコード種別表）、3.3 構造の概要（文章・図形、画像、形式的定義＝BNF）、3.4 構造の詳細（管理情報、文章開始／終了、図形開始／終了、画像、仮身、機能付加、設定付加）。

| 画像・仮身・機能付加・設定付加・管理情報 | なし | 未実装 |
| 標準 TAD（付録B） | なし | 未調査 |

**要確認（重大）**: 表の欠落が多く、**ID の割当・フィールド配置・BNF の形式的定義（3.3.4）が読めていない**。特に 0xA0〜0xAF が「文章付加」で 0xB0〜0xBF が「図形」という割当は、見出しの数字とセグメント名から再構成したもので、**文章／図形の開始・終了セグメントや 0xE0 台の ID は取得できていない**。TAD は適合の中核なので、原文（画像を含む）を直接確認する工程を設ける。
**試験**: セグメント単位の往復試験、既知の TAD ファイルを読んで書き戻し一致を見るテストベクトル（入手経路は未定。無ければ自作し、相互運用試験は別途）。
**方針（案）**: バイト順の変換は TAD の入出力境界に閉じる。仮身セグメントは実身・仮身モデル（#46、[btron3-file-design.md](btron3-file-design.md)）と同時に設計する。

## 4. フロッピーディスク形式（fd_format.html）

### 要求の要約
- 目的: TRON 系システム間でアプリとデータを持ち運ぶ形式。論理ブロックをセクタにまとめ、大きいファイルは索引で引く。
- ディスク構成: システムブロック（全体情報）→ ファイル ID 表 → ファイル短縮名表（高速検索用）→ ファイル領域。ファイル領域の先頭はルートファイル。
- ファイル構成: ヘッダブロック（ファイルヘッダ：種別・属性・時刻・名前・アクセス／共有情報）、断片表（空き領域の管理。結合・分割）、レコード索引（直接／間接／リンク）、間接索引、データブロック。リンクファイルは最小のデータのみ。
- 付録A: 標準フロッピー形式（ビットマップ・バイト順の規約）、付録B: TRON プロファイルのフロッピー形式（題名が切れている）。

### 照合

| 項目 | 既存実装 | 状態 |
|---|---|---|
| システムブロック・ID 表・短縮名表・ファイル領域 | なし（RAMFS は形式と無関係。篇藏は設計・F0〜F3 の内部形式） | 未実装 |
| ファイルヘッダ／断片表／レコード索引 | なし | 未実装 |
| 物理ディスクへの読み書き | なし（仮想ブロック装置は F8） | 未実装 |

**要確認**: 式（ID 表・短縮名表・セクタ大きさ）が崩れている。4.2.2・4.3.4・4.3.6・4.3.7・付録B が欠落または破損。**このイメージ形式は 1.6 のファイル管理の外部表現であり、内部の篇藏とは分離する**（Phase 4）。実装は仮想ブロック装置（F8）の後でよく、優先度は低い。
