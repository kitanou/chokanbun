## 2. 表示装置の第 1 段階（実装済）

- **装置**: `virtio-gpu-device`。QEMU には `-global virtio-mmio.force-legacy=false` と `-device virtio-gpu-device` を付ける。**主な試験の起動には付けない**（頁の総数を固定した試験があるため。専用の短い起動だけで使う）。
- **初期化は遅延**: 最初の `画面出` で、機器表（Devicetree）が教える virtio-mmio の枠から DeviceID 16 を探して初期化する。起動時には何も探さず頁も取らない。装置が無ければ `画面出` は `-ENOENT`。
- **提示の手順**（呼ぶたびに）: （資源が無い・大きさが違えば）2D 資源の作成 → 背面の割り当て → （新しい資源なら）走査出力の設定 → ホストへ転送 → 表示の更新 → 背面の取り外し。**走査出力は背面が付いた資源にしか設定できない**（QEMU が `ERR_UNSPEC` を返す）ので、割り当てが先。取り外しまで行うので、行程が終わって塊が頁池へ戻っても、装置があとでその頁を読むことはない（2D 資源はホスト側に画面の写しを持つので、取り外したあとも表示は残る。screendump で確認済み）。
- **背面**: 行程の広域（漢令 123）の 2 MiB 塊 1 つ（物理は連続）。幅 × 高 × 4 ≤ 2 MiB。
- **画素の形式**: virtio-gpu の `X8R8G8B8_UNORM`（4）。メモリ上のバイトが先頭から X・R・G・B の順で、ディスプレイプリミティブの 32 ビット画素（上位バイトが先、値 `0x00RRGGBB`）と一致する。赤・緑・青の帯を描いて screendump で確かめた。
- **漢令 233 `画面出`**: x0＝広域の 2 MiB 塊の先頭、x1＝幅、x2＝高。戻り値 0、引数不正は `-EINVAL`、塊でない番地は `-EFAULT`、装置が無ければ `-ENOENT`、装置の誤りは `-EIO`。（232 は永続化の試験が使っているので 233 にした。）
- **EL0 の入口**: `dp.mkn` の `gopn_dev("SCREEN")` が広域の最初の塊を 320×240 のビットマップとして描画環境にし、`gfls_dev`（原文に無い、この実装の追加）が提示する。
- **制約**: 単独の持ち主（広域は行程ごと）。ウィンドウマネージャが共有する画面は後の段階。画面の大きさは 320×240 固定。

## 2b. 入力装置の第 1 段階（実装済: キーボードとタブレット）

- **装置**: `virtio-keyboard-device`（DeviceID 18）。タブレット（`virtio-tablet-device`）も DeviceID 18 なので、設定空間の `EV_BITS`（選択 0x11）の `EV_ABS`（副選択 3）の大きさが 0 のものをキーボードとする。キーボードは種 0、タブレットは種 1 で、それぞれ別の状態の語（`0x403FF008`・`0x403FF010`）と環を持つ。
- **初期化は遅延**: 最初の `入力汲`（または `事取`）で探して初期化する。装置が無ければ状態の語（`0x403FF008`）に「無し」を覚えるだけで、頁も取らない。
- **事象キュー**: キュー 0 に 8 バイトの受け口を 8 つ先に渡し、使用済み環を読んで、同じ受け口を戻す（`kernel/proc/inp.mkn`）。割込は使わずポーリング。状態キュー（キュー 1）は使わない。
- **イベント管理への接続**: `EV_KEY` の値 1 を `EV_KEYDWN`（3）、値 0 を `EV_KEYUP`（4）として、`put_evt` と同じ本体（`事生内`、指定 7: 現在の PD 位置・メタ状態・時刻を付ける）で隊へ積む。値 2（自動反復）は模型が自前で出すので捨てる。**システムイベントマスクの既定は 0 なので、`chg_emk` でキーの種別を有効にしたときだけ隊に載る**（`put_evt` と同じ規則）。
- **汲み取りの時機**: 漢令 234 `入力汲`（引数なし。積んだキー事象の数、装置が無ければ `-ENOENT`）と、`事取`（`get_evt`）の先頭。
- **タブレット**: `EV_ABS` の X・Y（0〜32767）を画面 320×240 の PD 位置（模型の `端横`・`端縦`）に直して覚える（位置だけでは事象を出さない）。`BTN_LEFT`（0x110）の押下を `EV_BUTDWN`（1）、解放を `EV_BUTUP`（2）として、現在の PD 位置を座に付けて隊へ積む。他のボタン・ホイール・相対移動は未対応。
- **キートップ**: evdev のキー符（下位 8 ビット）をそのまま使い、文字コードは 0。BTRON3 のキートップ番号・文字コードへの対応表は、原文の図が手元に無く確かめられないため未実装。
- **試験**: `tests/run_tests.sh` の `inp_boot`。`描試 K` が `chg_emk` でキーを有効にして待ち、モニタの `sendkey a`・`sendkey b` で押したキーを `事取` で読み、`EV_KEYDWN`・`EV_KEYUP` の順と、キートップ 30・48 を確かめる。タブレットは `描試 T`（ボタン種別を有効にして待つ）と、QMP の `input-send-event`（HMP の `mouse_move` は相対移動を送るのでタブレットには届かない）で絶対座標 (16384, 16384) と左ボタンの押下・解放を送り、座 (160, 120) と `EV_BUTDWN`・`EV_BUTUP` を確かめる。装置を付けない起動では `-ENOENT`。

## 3. 試験の方法

QEMU のモニタ（`-monitor unix:<ソケット>`）の `screendump` で PPM を取り、画素を調べる（`tests/run_tests.sh` の `gpu_boot`）。

- 画面の用意: 外部命令 `描試 G` が `SCREEN` を開き、赤・緑・青の帯・黒の縁・白い隅を描いて `gfls_dev`、さらに右上を赤紫にして 2 回目の提示。印（`描試 再提示`）が出たら `screendump` を取る。
- 確かめること: 320×240、帯と隅の画素値、2 回目の提示が反映される（資源を作り直さない経路）、装置を付けない起動では `-ENOENT`。
- 注意: モニタのソケットの経路は 104 バイトまでなので `/tmp` に作る。`screendump` のファイル名に空白があるときは `"` で囲む。
- 主な起動（装置なし）でも、`SCREEN` の環境の生成・仕様の取得・描画・読み戻しは試験できる（`描試` の 5 項目）。

## 4. 次の段階

1. **入力の残り**: タブレットの他のボタン・ホイール。キートップ番号と文字コードの対応表（原文の図で確かめる）。割込駆動（今はポーリング）。
2. **画面の共有**: 画面を核が持ち、複数の行程が描画環境（`MSGPNL` を含む）を開けるようにする。ウィンドウマネージャの前提。
3. **文字描画**: フォント形式（共有データ編・3.9）と TRON コードの B〜D ゾーンの割当（出典を探す）。2.5 の関数。
4. **ウィンドウマネージャ（3.1）**: ウィンドウの生成・移動・再描画・イベント配送。漢殻からの起動と、GUI が止まったときの漢殻での診断・復旧（F7 の残りの項目）。
5. **描画関数の残り**: 曲線・円弧・楕円・多角形（画素の決め方は原文の図に頼る）、パターンマスクのビット配置（図 29）、カラー情報つきの環境、クリッピング領域。
